## [三星与 SK 海力士据报将通过交叉许可采用长江存储 Xtacking 技术](https://t.me/zaihuapd/45377) ⭐️ 8.0/10

据报三星电子与 SK 海力士已通过交叉许可协议，同意在 3D NAND 闪存生产中采用长江存储 Xtacking 键合技术的部分内容。三星、SK 海力士和长江存储三方均对此拒绝置评，因此该消息目前尚未获得官方确认。 若消息属实，这将是中国存储厂商首次向占据主导地位的韩国 NAND 大厂授权核心工艺技术，说明长江存储的混合键合路线已难以被忽视。这可能加快整个行业从传统单晶圆 NAND 制造方式转向键合方案，并改变 3D NAND 关键知识产权的分布格局。 Xtacking 的做法是把存储单元阵列与控制电路（CMOS）分别制造在两片晶圆上，再通过键合工艺合二为一，使两部分可以各自独立生产与优化。Omdia 一位高级分析师指出，这样厂商可以自行生产存储阵列，而把逻辑电路交给晶圆代工厂，从而用上更先进的制程；不过相比更简单的 CMOS-under-array 方案，键合工序的成本与良率仍是主要代价。

telegram · zaihuapd · 11月26日 05:30

**背景**: 3D NAND 闪存通过垂直堆叠存储单元来提升密度，而负责驱动这些单元的周边 CMOS 电路传统上要么放在阵列旁边，要么放在阵列下方（即 CMOS-under-array）。较新的替代方案是把 CMOS 晶圆与 NAND 阵列晶圆分别用各自优化的工艺制造，再通过密集的铜对铜接触焊盘进行晶圆对晶圆混合键合，将两者结合。中国 NAND 厂商长江存储正是以 Xtacking 为名率先推动了这种分晶圆键合路线。

## [面向廉价 gfx906 HBM2 数据中心 GPU 的 AMD 专用 llama.cpp 分支](https://devnull.land/amd-specific-llama-cpp) ⭐️ 7.0/10

一位开发者发布了 llama.cpp 的 AMD 专用分支，专门针对 gfx906 系列数据中心 GPU（2018 年的 Vega 20 芯片，用于 Instinct MI50/MI60 和 Radeon VII）进行优化，这些卡没有张量核心，也不原生支持 bf16。该分支让二手卡也能跑出可用的本地大模型推理性能——这类卡以约 200 美元的价格提供 32GB HBM2 显存和约 1 TB/s 的带宽。 本地大模型的逐 token 解码受显存带宽限制，因此老一代高带宽加速卡能以极低价格提供接近昂贵新卡的性能。该分支降低了在本地运行大型量化模型的门槛，也说明社区优化可以让官方软件栈基本放弃的硬件继续发挥余热。 由于 gfx906 没有张量核心，也不原生支持 bf16，该分支只能依赖手工调优的 kernel 和针对量化格式的专门路径，而无法像 NVIDIA 或更新的 AMD 硬件那样走张量核心快通道。它注定是一个小众且维护成本较高的项目，实际性能高度依赖于具体模型、量化格式以及所使用的 ROCm 版本。

hackernews · julianlam · 11月26日 17:11 · [社区讨论](https://news.ycombinator.com/item?id=50657265)

**背景**: llama.cpp 是一个基于 ggml 库的开源 C/C++ 推理引擎，只需极少配置就能在 CPU、GPU 等多种硬件上运行量化后的 GGUF 模型。gfx906 是 AMD Vega 20 架构的 LLVM 目标名称，2018–2019 年以 Instinct MI50/MI60 数据中心卡和 Radeon VII 的形式发售，其特点是计算吞吐一般，但配备了带宽极高的 HBM2 堆叠显存。HBM2 是一种 3D 堆叠的 DRAM 接口，带宽远超 GDDR 或系统内存，而这正是受带宽限制的大模型解码最需要的。

## [sqlite3_rsync：无需双倍磁盘空间即可远程快照 SQLite 数据库](https://simonwillison.net/2026/Nov/26/sqlite3-rsync/) ⭐️ 6.0/10

Simon Willison 指出了 SQLite 实验性工具 sqlite3_rsync 一个此前被低估的特性：它可以通过 SSH 把数据库快照复制到另一台机器上，而无需先在本地创建完整副本。该工具最早在 2024 年 10 月的 SQLite 3.47.0 中作为实验性功能加入，并在 2025 年 5 月的 SQLite 3.50.0 中得到增强，因此这更像是一篇解读文章而非新版本发布。 传统快照 SQLite 数据库的方式——备份 API 和 VACUUM INTO——都需要足够的空闲磁盘来存放一份完整副本，而对于已使用超过一半存储空间的小型实例来说这根本做不到。sqlite3_rsync 打破了这一限制，使资源受限的部署（如边缘设备、小型 VPS 实例和嵌入式系统）也能实际执行远程备份和副本同步。 该协议的工作方式与 rsync 类似：副本端把数据页或页组的加密哈希值发送给源端，源端只返回内容有差异的页面，或在多页哈希不匹配时请求更细粒度的哈希。如果两端初始差异极大，由于哈希交换的开销，总带宽可能略超整个数据库的大小，但超出部分最多只有几个百分点。

rss · Simon Willison · 11月26日 06:08

**背景**: SQLite 是一个自包含的 C 语言库，无需独立的服务器进程即可实现完整的 SQL 数据库引擎，被广泛认为世界上部署量最大的数据库引擎。由于 SQLite 数据库就是一个单独的文件，在其被使用时做一致性备份通常需要特殊机制，而不能简单地复制文件。备份 API 和 VACUUM INTO 都能生成一致性副本，但二者都会在本地写出一个完整的新数据库文件，从而使所需磁盘空间翻倍。sqlite3_rsync 则借助基于哈希的差异协议通过 SSH 传输变更，思路与经典的 rsync 工具一脉相承。
